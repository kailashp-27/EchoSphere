Project Overview
EchoSphere is a personal learning environment that organises study documents and notes and provides AI
summaries, explanations, flashcards, exam questions, knowledge graphs and knowledge-base chat. The
current release combines a React interface, an Express API, MongoDB persistence, LanceDB retrieval and
local Ollama models.
Problem Statement
Students and researchers keep useful knowledge across separate documents and notes. Finding relevant
passages, revising long materials and connecting related concepts takes time. EchoSphere brings these
materials into one workspace and provides study outputs derived from selected documents or retrieved
knowledge-base context.
Users and Objectives
The primary users, carried forward from DA1, are university students preparing for assessments and
researchers reviewing a collection of papers. The objective is to reduce retrieval and revision effort while
keeping the source material available for checking AI output.
Report Scope
This report presents the project requirements, system design, implementation and completed DA3 testing.
The recorded results include 64 passing Jest tests, 33 passing Postman assertions across 22 live requests, a
92.28 percent mutation score for request validation, and successful frontend and Docker image builds.
Automated tests, live API tests and selected browser workflows were verified separately.

System Architecture and System Design

Current architecture: MongoDB holds application records; uploaded files remain on disk; LanceDB stores
indexed text chunks; Ollama provides local generation and embeddings.
The modular frontend and REST API separation follow the principles described in DA2. Knowledge routes
manage folders, documents and notes; tools routes generate study outputs; graph and prompt routes
persist their own records. RAG utilities handle chunking, embeddings and retrieval.
Uploaded files and notes are saved first, then vector ingestion runs in the background. Chat retrieves
relevant LanceDB chunks; summarisation, explanation, flashcards, exam questions and graph generation
read selected document text directly. Ollama is a host service outside the frontend/backend/MongoDB
Compose services.

Implementation and Module Responsibilities
Frontend and user interaction
React and TypeScript implement the dashboard, knowledge base and study workspaces. Tailwind CSS
provides the layout and light/dark presentation. The persistent sidebar keeps navigation consistent with
the DA2 wireframes. Each workspace holds its selection, loading, result and error states; HTTP requests
connect it to Express. The summary workspace displays source text beside generated output so the learner
can compare them.
Knowledge ingestion and storage
A learner creates a folder, uploads a supported file or writes a note. Multer receives uploads with a 50 MB
limit. PDF text is extracted using pdf-parse, DOCX text using mammoth, and TXT files are read as text.
MongoDB stores metadata and notes, while original uploads remain in the configured upload directory.
Web clipping uses fetch and cheerio to extract readable page content and save it as a note; success
depends on network access and page structure.
Generation and retrieval
Document tools obtain the selected record and extract its text before calling Ollama. The concept explainer
also accepts a topic without a document. Flashcards, exam questions and graphs request structured JSON
so their outputs can be rendered as interactive components. Chat follows a separate RAG path: text is split
into overlapping chunks, nomic-embed-text creates embeddings, LanceDB retrieves relevant chunks, and
the selected generation model composes an answer from the retrieved context.
Module Main responsibility
knowledge.js Folder, file, note, download and web-clipping operations.
tools.js Summary, explanation, flashcards and exam-question generation.
graph.js and prompts.js Graph generation/persistence and reusable prompt storage.
rag.js and validation.js Chunking, embeddings, retrieval, shared generation and request validation.

The generation model used in the recorded demo is llama3.2:1b. Local Ollama calls do not require a Gemini
API key. Model selection and the theme preference are stored in the browser; application records remain
in MongoDB.

Test Execution Method and Acceptance Criteria
Repeatable automated checks
Jest runs the backend suite in one worker and Supertest sends requests directly to the exported Express
application. The integration tests connect to a real MongoDB instance at 127.0.0.1:27018 using the
echosphere_jest database. AI generation and indexing are stubbed in this suite so failures can be attributed
to application behavior rather than varying model output. The test upload directory is artifacts/jest-
uploads; the suite drops its disposable database after execution.
Live integration checks
The Postman collection runs in order because later requests reuse identifiers created by earlier requests. It
creates a folder and note, saves a prompt, calls the live study tools, saves/retrieves a graph, updates a note
and exercises invalid inputs. A request passes only when its assertions pass: for example, a folder must
return HTTP 201, appear in the subsequent list, and provide an identifier for dependent operations.
MongoDB and Ollama are real services in this run.
Expected results and negative cases
A successful summary or explanation must return HTTP 200 with non-empty result text. Flashcards must
contain question/answer fields, exam responses must contain questions, and graphs must contain nodes
and links. Blank names, missing document selections, invalid counts and malformed chat history should
return HTTP 400 with JSON error information. Unknown API paths should return JSON 404. These checks
establish response behavior; they do not grade the educational correctness of every generated statement.
Regression and mutation checks
Regression tests repeat the expected workflows after fixes to detect unintended changes. Stryker then
mutates backend/validation.js and reruns the tests. A killed mutant means the tests detected a changed
behavior; a surviving mutant identifies a possible test weakness or equivalent behavior requiring review.
This gives additional evidence about the validation tests, rather than measuring the whole application.
Reproduction commands
With the disposable MongoDB service available, run npm test and npm run test:mutation from backend.
Import EchoSphere.postman_collection.json into Postman and run its requests in order against the
configured local backend. Use the Desktop Agent for Postman web because the Cloud Agent cannot reach
localhost. TESTING.md records the isolated service configuration and the original run instructions.
The recorded automated results comprise 64 passing Jest tests, 33 passing Postman assertions and a 92.28
percent mutation score for request validation. Browser checks provide additional evidence for selected
user workflows; they do not replace the automated suite or establish exhaustive coverage of the final
application.

Appendix A Software Requirements Specification
Purpose: provide a single-user local workspace for storing personal study materials and creating AI-assisted
revision outputs. The requirements below describe the current release and its intended operation.
ID Functional requirement
FR01 Accept PDF, DOCX and TXT uploads and store their metadata and original files.
FR02 Create, edit, list and delete notes; organise records within hierarchical folders.
FR03 Extract readable text and perform background chunking, embedding and vector indexing.
FR04 Generate selected-document summaries, explanations, flashcards, exam questions and graphs.
FR05 Persist and retrieve graph nodes/links and saved prompts.
FR06 Answer knowledge-base chat queries using retrieved context where available.
FR07 Allow local model selection, theme preference and consistent workspace navigation.
FR08 Validate supported request inputs and return clear JSON errors for rejected operations.

Constraints and Nonfunctional Requirements
The system requires local MongoDB and Ollama with the generation and embedding models installed. File
uploads are limited to 50 MB. OCR, multi-user authentication and performance prediction are outside the
implemented release. Existing automated tests cover specified behaviors; they do not establish security for
public deployment, arbitrary-document parsing accuracy or guaranteed hallucination-free answers.

Arrow, pdf-parse, mammoth, cheerio, Ollama, react-force-graph-2d, Git, Docker Compose, Postman, Jest,
Supertest and Stryker.
Quality requirements and current status

Maintainability is supported by route modules, shared validation, environment configuration and saved
tests. Reliability is assessed through the recorded request and persistence checks. The original speed,
uptime and near-zero hallucination goals remain targets: no load test, long-duration availability
measurement or systematic factual-accuracy benchmark is included.

Appendix B Data Flow Diagram

The DFD summarises learner inputs, knowledge ingestion, record management and study-output
generation, with MongoDB, file storage and LanceDB as data stores.
Ingestion validates and saves input, extracts text and indexes embedded chunks asynchronously. Study
tools obtain selected document text or retrieved context and call Ollama. Web clipping fetches a supplied
web page and stores readable content as a note; this workflow requires network access.
Inputs and outputs
The learner supplies a file, note, topic or question. Ingestion produces stored records, original files and
vector chunks. Study generation produces text, structured cards/questions or graph nodes and
relationships. Only chat depends on retrieved vector context; selected-document tools read source text
directly.
Failure and timing considerations
A stored note can appear before its background vector ingestion completes. Therefore, immediate chat
availability must not be inferred from a successful save response. Missing files, unsupported formats,
unavailable models and generation errors are distinct failure paths. The UI should show the returned error
while preserving the learner selection so it can be retried.

Appendix C Entity Relationship Diagram

Logical relationships reflect the current MongoDB schemas. A document or note can belong to one optional
folder, while a folder can contain many records.
Folder.parentFolderId models nesting. Graph.documentId is unique and logically identifies a document or
note, although MongoDB does not enforce a foreign key. Nodes and links are embedded in Graph;
SavedPrompt is independent. Vector chunks reside in LanceDB and carry documentId associations.
Record responsibilities
Document records identify uploaded source material and its type; Note records contain editable text,
including the current web-clipping output. Folder records provide names and optional parent links. A Graph
embeds nodes and links for its source document identifier. SavedPrompt records hold reusable prompt text
and category information. LanceDB chunks associate vector content with the originating document
identifier for retrieval.
Consistency considerations
The relationships are logical rather than enforced relational foreign keys. Application routes must handle
deletion and movement consistently, retain graph metadata and refresh note vectors when content
changes. The automated suite checks selected lifecycle cases, but it does not establish correctness for
every possible interrupted indexing or concurrent-update scenario.

Appendix D UML Use Case Diagram

The learner interacts with document management, study tools, knowledge-base chat, saved prompts and
local model configuration.
The single-user actor follows the DA1 scope. Multi-user JWT login and image OCR are excluded from this
release. Flashcards, exam questions and chat extend the original summary, explanation and graph
workspaces.
Example use case
To revise a document, the learner uploads it, confirms that it appears in the knowledge base, selects it in a
study workspace and requests an output. The system reads its text, calls the chosen model and renders the
result. The learner can then check the source, flip generated flashcards, reveal an exam answer or save the
generated graph.
Preconditions and exceptions
The backend and MongoDB must be reachable, a supported source must be stored, and Ollama must have
suitable generation/embedding models available. If a document is missing or input is invalid, the API should
reject the request. If model loading fails, the error must be shown rather than presenting an empty output
as successful completion.

Appendix E UML Sequence Diagram

The sequence shows the successful knowledge-base chat path from the browser request through query
embedding, vector retrieval and response generation.
The main chat request is POST /api/chat. If no relevant vector chunks are returned, the implementation
falls back to document titles or an empty-knowledge-base message. That fallback does not establish the
contents of a document; users should check generated answers against their sources.
Sequence responsibilities
The browser submits a question and bounded chat history to Express. The backend embeds the query,
searches the vector store, builds a context prompt and requests generation. The completed answer is
returned as JSON and appended to the conversation.
